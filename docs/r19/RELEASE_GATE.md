本次整合目標是 Suite 17.4.0：保留 Suite 17.3.2 的 28 項工具登記資料，再加入固定來源的 R19，合計 29 項工具、24 個獨立資產、29 個 Release 附件與 15 個離線 HTML。R19 維持 `PREVIEW`；完整身分與封包契約見 [Suite 17.4.0 整合契約](SUITE_17_4_0_RELEASE.md)。

## 必須依序完成的工程檢查

1. **固定來源與舊工具身分。** 保留前 28 項工具的完整登記資料、原版號、來源 SHA 與固定工具 bytes；加入的 R19 HTML、runtime、helper、template、builder 與原 runner 保持原樣。來源固定值見整合契約。不得藉修改 runner、放寬斷言或變更來源讓驗收通過。
2. **完整套件登記。** registry、manifest、封包、六語入口與實際附件須一致，精確符合 29／24／29／15 的數量。原有工具不能遺漏、改名替代或只保留文件連結。R19 是產品變更，不適用文件專用的免發版例外。
3. **最終候選的本機檢查。** 執行相關 Node、Python、公開檔案、第三方權利、六語來源同步、固定 metadata、generated-artifact parity 及完整套件檢查。原生條件被略過、以 echo 取代執行、錯誤被忽略、舊 metadata 被改寫或封包 bytes 不符時，都必須失敗。
4. **最終 PR CI。** 必要 CI 成功，且既有 `browser-integration` job 實際執行原始 R19 十情境與原 validator。這些步驟不得被分支限定條件略過，也不能以 `continue-on-error`、`|| true` 或偽造報告當成通過。審查必須對應最後提交；有新變更就重跑相關必要檢查。
5. **合併後 main CI。** main 上的最終提交也須實際執行原生十情境及收據驗證。中央發行 job 維持依賴 `verify` 與 `browser-integration`；不能只憑 PR 的較早結果直接發布。
6. **正式來源建置與 staging。** 從準備發布的精確提交建置新套件。舊官方 Release 資產只能取回原始附件並驗證固定 SHA；缺件、雜湊不符或來源不明時停止。保留 MRFT 既有生成特例與其固定驗證；不得以重建取代舊 R5／R6 等官方資產。
7. **Draft 的全部附件下載核對。** `all-tools-suite-v17.4.0` 必須對應預期提交，附件名稱、數量與 staging 完全一致。將全部 29 個附件下載至空目錄，核對 SHA、ZIP CRC、manifest、內嵌工具與入口。API metadata 或上傳成功本身不足以通過此步。
8. **發布後再下載核對。** Draft 核對成功後才公開；公開後再下載全部附件至另一個空目錄，重新驗證同一組身分與 bytes，保留發行收據。只有這一步也成功，才能記錄 `RELEASE_OK`。

任一條件失敗，就記錄實際失敗步驟並停止推進。保留既有 `all-tools-suite-v17.3.2` tag 與附件；不得覆寫舊版本、重用舊 tag 或恢復已撤回的整合包。若公開後驗證失敗，應記錄當時的實際公開狀態與失敗結果，不得宣稱發行已驗證完成；依發行器的恢復程序處理。

## 原生通過的範圍

原 runner 的十情境涵蓋指定的匯入與應用內取消、來源改變、過期預覽、偏好、候選超限、真實下載、窄版、鍵盤及零外部請求。精確測試提交與證據見[原生驗收紀錄](NATIVE_ACCEPTANCE_R2.md)，驗證器與留存限制見[驗證方式](TESTING.md)。

原 validator 檢查報告格式、來源 SHA、版本宣告與 PNG 標頭／尺寸；它不重新執行瀏覽器，也不獨立重驗每份下載檔。原候選 artifact 沒有保留每次下載的原始 bytes；下載結論來自原 runner 的真實下載斷言及其執行紀錄。

作業系統選檔視窗及取消流程仍未測。真人操作、E1/E2/E3/D7、母語自然度、原意等價與使用者採用維持延後／未量測，與本次工程預覽發行分開記錄。工程 Gate 或正式發布成功，都不能把這些項目改寫為已驗證。

R19 沒有更換凍結核心、擴充未審詞庫、連線 Provider 或開啟遙測。文件偏好只是使用者主動記下的提示，每一處仍須確認。更廣的功能需要各自的範圍、測例與發行驗證。
